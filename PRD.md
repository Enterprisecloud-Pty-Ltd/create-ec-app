# PRD: Scoped CSS and Embeddable Styling for `create-ec-app`

## 1. Title

Scoped CSS by default for shadcn/Tailwind apps generated by `create-ec-app`, including safe PCF conversion for Dynamics 365 / Power Apps model-driven forms.

## 2. Status

Proposed.

## 3. Problem statement

`create-ec-app` can generate React + TypeScript web resources using Tailwind CSS and shadcn/ui, then convert those web resources into PCF controls. The current generated CSS is not safe to inject into a host page such as a Dynamics 365 model-driven form because the CSS is global.

The practical failure mode is:

1. A generated web resource imports Tailwind/shadcn CSS globally.
2. The app is later converted to a PCF control.
3. The PCF wrapper imports the generated `dist/main.css`.
4. That CSS is injected into the model-driven app page.
5. Tailwind Preflight, unprefixed utility classes, shadcn theme variables, global `body`, global `*`, and global `.dark` selectors can affect Dynamics 365 form controls or other PCF controls on the same form.

The required product behavior is:

> Every generated app must behave as an embeddable widget by default. Its CSS must be scoped to that app instance and must not leak to the host page.

This must be true for standalone Vite usage, Dataverse web resources, Power Pages, and PCF conversion.

## 5. Product goal

Generated apps must be safe to embed in a larger host page without overriding host-page styling.

The new default invariant is:

> All generated apps are scoped by default.

The app must always render inside a stable root boundary class:

```txt
.ec-app
```

All generated shadcn/Tailwind base styles and theme variables must live under `.ec-app`.

For PCF, the PCF container must also retain:

```txt
.ec-pcf-shell-control
```

but CSS scoping should use `.ec-app` as the universal boundary.

## 6. Users

Primary users:

1. Developers generating Dataverse web resources with `create-ec-app`.
2. Developers converting generated web resources into PCF controls.
3. Developers embedding generated apps in Power Pages or other host pages.
4. Makers and end users using model-driven app forms that contain standard Dynamics controls plus generated PCF controls.

## 7. Goals

### G1. Universal scope boundary

Every generated app must render inside `.ec-app`.

### G2. No global Tailwind Preflight leakage

Generated app CSS must not import Tailwind Preflight globally.

Do not use this in generated CSS:

```css
@import "tailwindcss";
```

Instead, import Tailwind theme and utilities explicitly, with a prefix, and omit `tailwindcss/preflight.css`.

### G3. Tailwind utility namespacing

Generated Tailwind utility classes must be prefixed using the Tailwind v4 prefix syntax.

Use the Tailwind CSS import namespace:

```css
prefix(ec)
```

Generated class names must use the Tailwind v4 class prefix form:

```tsx
ec:flex
ec:grid
ec:hidden
ec:border
ec:bg-background
ec:text-foreground
ec:hover:bg-accent
ec:focus-visible:ring-ring
```

Do not use unprefixed Tailwind utility classes in generated shadcn UI components.

Do not use Tailwind v3-style prefixed classes like:

```tsx
ec-flex
ec-bg-background
```

### G4. shadcn CSS variables scoped to `.ec-app`

Move shadcn theme variables from global selectors to `.ec-app`.

Replace:

```css
:root { ... }
.dark { ... }
body { ... }
* { ... }
```

with app-local equivalents:

```css
.ec-app { ... }
.ec-app.dark,
.ec-app .dark { ... }
.ec-app { background: var(--background); color: var(--foreground); }
.ec-app * { ... }
```

### G5. Radix/shadcn portals must not escape the app root

Any shadcn component that uses Radix Portal or a portal-like library must render portal DOM inside the `.ec-app` subtree, not under `document.body`.

This applies to at least:

```txt
alert-dialog
context-menu
dialog
drawer
dropdown-menu
hover-card
menubar
popover
select
sheet
sonner/toaster
tooltip
```

The implementer must inspect all shadcn components under:

```txt
templates/ui/shadcn-ui/src/components/ui
```

and update every portal usage that supports a custom container.

### G6. Existing generated app behavior must remain normal in standalone/webresource mode

Scoped-by-default must not make the app look different when running locally as a normal Vite app or deployed as a web resource.

### G7. PCF conversion must become safe by default for newly generated apps

When a newly generated shadcn app is built and converted to PCF, the resulting PCF control must not leak global Tailwind/shadcn styling to the Dynamics host form.

## 8. Non-goals

The following are explicitly out of scope for this change:

1. Full Shadow DOM migration.
2. Building a CSS postprocessor that can reliably rewrite arbitrary third-party CSS.
3. Automatically migrating every arbitrary existing user project created before this PR.
4. Fully scoping Kendo UI theme CSS.
5. Changing the visual design of shadcn components.
6. Replacing shadcn/ui or Tailwind.
7. Rewriting the PCF packaging model beyond what is required for scoped CSS and portals.

## 9. Required design

### 9.1 Universal app shell

Add a reusable generated app shell to the base template.

Recommended file:

```txt
templates/base/src/runtime/EcAppShell.tsx
```

Expected behavior:

1. Renders a `.ec-app` root.
2. Provides a portal container inside `.ec-app`.
3. Exposes a hook that shadcn components can use to obtain the portal container.
4. Does not depend on shadcn.
5. Is safe for Kendo and non-shadcn apps.

Example implementation:

```tsx
import * as React from "react";

export const EC_APP_SCOPE_CLASS = "ec-app";
export const EC_PCF_SCOPE_CLASS = "ec-pcf-shell-control";

const EcPortalContainerContext = React.createContext<HTMLElement | null>(null);

export function useEcPortalContainer() {
  return React.useContext(EcPortalContainerContext);
}

export function EcAppShell({ children }: { children: React.ReactNode }) {
  const [portalContainer, setPortalContainer] =
    React.useState<HTMLDivElement | null>(null);

  return (
    <div className={EC_APP_SCOPE_CLASS} data-ec-app-root="">
      <EcPortalContainerContext.Provider value={portalContainer}>
        {children}
        <div data-ec-portal-root="" ref={setPortalContainer} />
      </EcPortalContainerContext.Provider>
    </div>
  );
}
```

The exact file path may vary if the existing project conventions prefer another path, but the generated import path must be stable for both normal app rendering and PCF rendering.

### 9.7 Existing vendored shadcn components must use prefixed Tailwind classes

Update every vendored shadcn component under:

```txt
templates/ui/shadcn-ui/src/components/ui
```

so Tailwind utilities are prefixed with `ec:`.

Examples:

```tsx
"flex items-center gap-2"
```

becomes:

```tsx
"ec:flex ec:items-center ec:gap-2"
```

```tsx
"hover:bg-accent hover:text-accent-foreground"
```

becomes:

```tsx
"ec:hover:bg-accent ec:hover:text-accent-foreground"
```

```tsx
"focus-visible:ring-ring focus-visible:ring-[3px]"
```

becomes:

```tsx
"ec:focus-visible:ring-ring ec:focus-visible:ring-[3px]"
```

```tsx
"[&_svg]:pointer-events-none [&_svg]:size-4"
```

becomes:

```tsx
"ec:[&_svg]:pointer-events-none ec:[&_svg]:size-4"
```

Do not generate invalid ordering like:

```tsx
"[&_svg]:ec:size-4"
```

Do not prefix non-Tailwind library class names that are required by third-party components unless they are Tailwind utilities.

The implementer must pay special attention to:

```txt
calendar.tsx
chart.tsx
sidebar.tsx
sonner.tsx
carousel.tsx
resizable.tsx
```

because these often contain third-party class names, custom data attributes, or library-specific selectors.

### 9.8 Portal support in shadcn components

All portal-enabled components must use `useEcPortalContainer()` from the generated runtime shell.

Example pattern:

```tsx
import { useEcPortalContainer } from "@/runtime/EcAppShell";
```

Then:

```tsx
function DialogContent(...) {
  const portalContainer = useEcPortalContainer();

  return (
    <DialogPrimitive.Portal container={portalContainer ?? undefined}>
      ...
    </DialogPrimitive.Portal>
  );
}
```

Apply this to all Radix portal components.

For libraries that are not Radix but still portal to `document.body`, inspect their APIs and pass the portal root when supported.

If a library does not support a custom portal container:

1. Keep the component functional.
2. Add a code comment explaining why it cannot be locally portaled.
3. Add the component to the PR notes under "Known portal limitations".
4. Do not silently ignore it.

### 9.9 PCF CSS import behavior

For this PR, keep the PCF generator importing the built CSS file:

```txt
dist/main.css
```

However, the built CSS must now be safe because newly generated source CSS is scoped.

Add a warning in `generatePcfFromExistingWebresource` when the CSS appears unsafe.

Recommended warning logic:

1. Read `<project>/dist/main.css`.
2. Detect obvious unsafe selectors:
   - global `body {`
   - global `:root {` containing shadcn variables like `--background`
   - global `.dark {` containing shadcn variables
   - Tailwind Preflight-style universal resets
   - unprefixed utility selectors such as `.flex`, `.grid`, `.hidden`, `.border`, `.text-sm`, `.bg-background`
3. If found, print a warning that the project appears to use unscoped Tailwind/shadcn CSS and may leak styles when deployed as PCF.
4. Do not fail the build unless a strict flag is added in the future.

This warning is for existing projects. New generated projects must pass the safe CSS checks.

## 11. Acceptance criteria

### AC1. Generated app root

A generated app must render with `.ec-app` present in the DOM.

Standalone/webresource DOM must include:

```html
<div class="ec-app" data-ec-app-root="">
  ...
  <div data-ec-portal-root=""></div>
</div>
```

PCF DOM must include:

```html
<div class="ec-pcf-shell-control">
  <div class="ec-app" data-ec-app-root="">
    ...
  </div>
</div>
```

The exact nesting can vary, but `.ec-app` must wrap all app UI and portal content.

### AC2. No global Preflight import

Generated CSS source must not contain:

```css
@import "tailwindcss";
@import "tailwindcss/preflight.css";
```

Built CSS must not contain Tailwind Preflight global reset behavior such as global margin/padding resets for all elements.

### AC3. shadcn tokens are scoped

Generated shadcn CSS must not contain global shadcn token selectors like:

```css
:root {
  --background: ...
}

.dark {
  --background: ...
}
```

It must contain:

```css
.ec-app {
  --background: ...
}

.ec-app.dark,
.ec-app .dark {
  --background: ...
}
```

### AC4. Body styles are not global

Generated shadcn CSS must not contain a global `body` theme rule.

This is forbidden:

```css
body {
  background: ...
  color: ...
}
```

This is required:

```css
.ec-app {
  background: var(--background);
  color: var(--foreground);
}
```

### AC5. Universal styles are not global

Generated shadcn CSS must not contain a global `*` shadcn base rule.

This is forbidden:

```css
* {
  @apply border-border outline-ring/50;
}
```

This is required:

```css
.ec-app * {
  ...
}
```

or an equivalent `:where(.ec-app *)` scoped selector.

### AC6. Tailwind utilities are prefixed

Vendored shadcn components must not use unprefixed Tailwind utilities.

Examples of forbidden class tokens in shadcn component className strings:

```txt
flex
grid
hidden
border
bg-background
text-foreground
hover:bg-accent
focus-visible:ring-ring
```

Required equivalents:

```txt
ec:flex
ec:grid
ec:hidden
ec:border
ec:bg-background
ec:text-foreground
ec:hover:bg-accent
ec:focus-visible:ring-ring
```

### AC7. Complex variants are valid

Complex variants must place the `ec:` prefix first.

Correct:

```txt
ec:[&_svg]:size-4
ec:data-[state=open]:bg-accent
ec:focus-visible:ring-[3px]
ec:dark:bg-background
```

Incorrect:

```txt
[&_svg]:ec:size-4
data-[state=open]:ec:bg-accent
focus-visible:ec:ring-[3px]
dark:ec:bg-background
```

### AC8. Portal DOM stays inside `.ec-app`

When opening these components, their rendered portal DOM must appear under `.ec-app`:

```txt
Dialog
AlertDialog
Sheet
Popover
DropdownMenu
ContextMenu
Select
Tooltip
HoverCard
Menubar
Drawer where supported
Sonner/Toaster where supported
```

DOM under `document.body` outside `.ec-app` must not contain the visual portal content for these components when a custom container API is available.

### AC9. PCF conversion preserves scope

After generating a shadcn webresource app, building it, and converting it to PCF:

1. The PCF control must build.
2. The PCF rendered DOM must include `.ec-pcf-shell-control`.
3. The rendered app must include `.ec-app`.
4. Opening shadcn popup UI must keep portal DOM inside `.ec-app`.
5. Standard Dynamics form controls outside the PCF control must not receive shadcn/Tailwind base styles.

### AC10. Build output safety checks

Generated `dist/main.css` for a new shadcn app must not contain unsafe global selectors for shadcn/Tailwind base behavior.

Forbidden or warning-triggering examples:

```css
body{...}
:root{--background:...}
.dark{--background:...}
.flex{display:flex}
.grid{display:grid}
.hidden{display:none}
.border{border-style:...}
.bg-background{...}
```

Expected examples:

```css
.ec-app{--background:...}
.ec-app.dark{--background:...}
.ec\:flex{display:flex}
.ec\:grid{display:grid}
.ec\:bg-background{...}
```

### AC11. Existing CLI commands still work

At minimum, these flows must work:

```bash
npm run build
```

Generate shadcn app:

```bash
npm run dev -- --project-name scoped-shadcn --target webresource --ui shadcn-ui --no-install
```

or equivalent supported CLI flags:

```bash
npm run dev -- --project-name scoped-shadcn --webresource --shadcn --no-install
```

Then inside generated app:

```bash
npm install
npm run build
```

Generate PCF from the built app:

```bash
npm run dev -- --pcf-dir ./scoped-shadcn
```

Then inside generated PCF folder:

```bash
npm install
npm run build
```

If exact scripts differ in generated PCF package, use the generated README instructions.

## 14. Edge cases

### 14.1 Multiple instances on the same form

Two PCF instances must not share portal containers.

Each `EcAppShell` instance must create its own portal root.

### 14.2 Dark mode

Dark mode must be local to the app instance.

This should affect only one app instance:

```html
<div class="ec-app dark">...</div>
```

This must not be required:

```html
<html class="dark">
<body class="dark">
```

### 14.3 Existing generated apps

Existing apps created before this change may still have unscoped CSS.

Do not attempt to rewrite arbitrary existing user source during PCF conversion.

Instead:

1. Ensure newly generated apps are safe.
2. Add warnings for unsafe existing CSS during PCF conversion.
3. Document that older projects should regenerate or manually migrate their shadcn CSS/components.

### 14.4 Third-party component class names

Do not blindly prefix every string token.

Some components may depend on library-specific class names or selectors. Examples may include React Day Picker, Recharts, Embla, Vaul, Sonner, or custom data attributes.

Prefix Tailwind utilities only.

### 14.5 `tw-animate-css`

When using Tailwind prefixing, import the prefixed animation export:

```css
@import "tw-animate-css/prefix";
```

Class names from the animation utility set should follow the same prefix model.

Examples:

```txt
ec:animate-in
ec:fade-in
ec:zoom-in-95
ec:slide-in-from-top-2
```

Do not leave unprefixed animation utilities in shadcn components if they are emitted by Tailwind/tw-animate-css.

## 16. Risks and mitigations

### Risk 1: shadcn CLI prefix handling may generate invalid complex variants

Mitigation:

1. Do not rely only on `components.json`.
2. Update vendored components directly.
3. Verify complex arbitrary variants manually.
4. Add acceptance checks for invalid `]:ec:` ordering.

### Risk 2: Portal components may lose styling if rendered outside `.ec-app`

Mitigation:

1. Provide `useEcPortalContainer()`.
2. Update every portal-capable component to pass the local container.
3. Manually test Dialog, Popover, Dropdown, Select, Tooltip, and Sheet.

### Risk 3: Some third-party components may not support custom portal containers

Mitigation:

1. Document the limitation.
2. Keep the component working.
3. Scope what can be scoped.
4. Add known limitations to PR notes.

### Risk 4: Kendo theme remains global

Mitigation:

This PR is focused on Tailwind/shadcn leakage. The universal `.ec-app` wrapper should be added for all generated apps, but full Kendo CSS isolation is a separate future work item.

### Risk 5: Existing user apps remain unsafe

Mitigation:

1. New apps are safe.
2. PCF generator warns about unsafe compiled CSS.
3. Documentation explains migration requirements.

## 17. Definition of done

This PR is complete when:

1. New generated apps render inside `.ec-app`.
2. shadcn generated CSS no longer has global `:root`, `.dark`, `body`, or `*` shadcn base styling.
3. Tailwind Preflight is not globally imported.
4. Tailwind utilities in shadcn components are prefixed with `ec:`.
5. `tw-animate-css/prefix` is used for shadcn animation utilities.
6. Radix/shadcn portals render inside the app-local portal container where supported.
7. New shadcn app build succeeds.
8. New shadcn app can be converted to PCF.
9. Generated PCF build succeeds.
10. CSS inspection confirms no obvious global Tailwind/shadcn leakage.
11. README/PCF docs explain the scoping behavior.
12. Existing PCF-specific class `.ec-pcf-shell-control` is preserved.
